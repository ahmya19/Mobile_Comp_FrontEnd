# Hosted-test tooling: safe under failure and concurrency (CP-39)

November 23. These are **test-tooling defects found by static review and reproduced locally with mocked transports and disposable PostgreSQL (PGlite) over the nine replayed migrations**. They are not evidence of a production RLS exploit, no unsafe path was run against the hosted project, and no phone, FCM send or hosted workflow was run. The earlier happy-path hosted runs remain valid for what they measured; they did not establish the failure guarantees below.

## Findings and resolution

| # | Finding (confirmed in current code) | Resolution | Proof |
| --- | --- | --- | --- |
| 1 | `workflow_hosted_regression.py`: failed owner/label/photo checks only cleared `ok`; the notification and history deletes still ran for the sole report inferred from "exactly one new report", and only the last delete checked owner and description. | Identity is proven by a **fresh on-device receipt** written by the test itself (report id and unique description, cleared before the run) AND the baseline difference equalling exactly that id AND owner, label and photo-path binding on the hosted row. Without proof nothing is deleted and the new IDs are recorded for review. Cleanup is **one guarded transaction** that locks the report row and re-verifies identity, the exact notification ids/owner, the history count, votes and SMS receipts, and refuses (rolling back) on any mismatch. | Python mocks (unrelated sole report, missing receipt, wrong owner, wrong marker, photo binding, guard refusal) and PGlite SQL (refuses with nothing deleted; late notice/history/vote refused; CONTROL shows the old statement sequence destroying an unrelated report's notices and history). |
| 2 | The same driver leaked cleanup and sessions on exceptions (photo download, SQL, JSON/JPEG, archive writing); `finally` only counted leftovers. | Setup, test, verification and teardown run under a guard that keeps the ORIGINAL failure, records it in the ledger, and still runs scoped cleanup (when identity was proven first) and teardown of every owned session. `--cleanup-only` finishes an interrupted run from its ledger with the same guards. | Download-failure test: run fails, scoped cleanup still ran once, sessions torn down, error recorded. |
| 3 | `hosted_authz_probe.py`: the four forbidden upload paths were not ledgered; absence was an aggregate count that could treat a new unauthorized object as pre-existing; the allowed upload relied on a success-only boolean. | Every exact bucket/path is written to the ledger before its upload; each path is checked on its own (presence read from the host, so a lost response cannot hide an object; a pre-existing path is a collision, not a result). An unexpected object fails the probe and stays in `cleanup_required`; the client only attempts deletes in the citizen's own `report-images` folder (never the originals bucket) and a successful removal is still reported as a policy regression. The allowed upload is recognised by host presence of its unique path. | Mocked tests: ledger complete before the first upload; unexpected original-bucket success; unexpected object in another account's folder; lost response; own-folder object removed but still a failure. |
| 4 | `real_fcm_probe.py`: the signed-out status change called the RPC directly, bypassing the per-send guard. | `change()` is the only status-RPC entry point and always runs the guard first; the signed-out case goes through it (zero registrations pass, any unexpected registration or changed citizen rows abort before send). | Stub tests: a new registration aborts with no RPC sent; zero registrations pass the same guard; source has exactly one status RPC call. |
| 5 | `sign_out_local` ignored HTTP failures; the FCM finish path swallowed network failures and still labelled the run cleaned; `hosted-voting-checks.py` stopped at the first failing role. | `hosted_safety` classifies each local logout as `confirmed` (200/204), `already-invalid` (401/403: the token is no longer accepted; this is not proof that this run's session was revoked) or `unresolved` (network, 5xx, anything else). Teardown attempts every owned session independently. Fixture cleanup and session cleanup are separate ledger fields and the exit code is non-zero if either is unresolved. The workflow, authz, FCM, phone and picker drivers use it; the voting checks now attempt every role before asserting. Storage checks and the map driver already recorded real outcomes (static review). | Mocked tests: one logout raising does not skip the other; 503 or network failure leaves `session_cleanup=unresolved` and a non-zero exit even when fixtures were cleaned. |

## Failing controls (safeguard removed, suite must go red)

Each was applied temporarily and the file restored: identity gate removed (1 failure), owner check removed (1), cleanup skipped on exceptions (4), logout failure reported as success (3), one failing logout skipping the next session (1), forbidden attempts not ledgered before upload (1), aggregate-only absence / lost response ignored (1), FCM guard removed from `change()` (2). Plus the SQL CONTROL test above.

## Limits

- `hosted_safety` cannot make Storage deletion transactional: the report delete is one transaction, the object delete is a separate API call verified afterwards (`object_cleanup`). A failure between them is visible as `fixture_cleanup=FAILED-object-still-present` and recoverable with `--cleanup-only`.
- The workflow driver cannot name the report id before the app generates it, so the on-device receipt is the narrow run-identity contract; it needs `run-as` access (debug build, emulator).
- A real no-push hosted smoke run of the changed workflow/authz drivers was not performed in this batch (no hosted workflow reruns allowed); the mocked and PGlite proofs are the evidence. Phone drivers were reviewed statically only and their changes are limited to the shared session and exit-code semantics.
