## Phase 2: real-screen audit (private screenshots, outside Git)

Screens captured on the real display with the owner's session in read-only browsing: Home, Report form (top and bottom), My Reports, Map and its stacked-marker chooser ("4 reports at this location", opens the correct details), Report Details, Notifications, Profile; font scale 1.3 on Home, Profile and the form (no clipped buttons; two-line wrapping only), restored to 1.0. Compared against the approved PDF's layouts; the camera, drafts, issue numbers, timeline, bottom bar and floating Report button are in place.

Defects found on the real screen and fixed:

- **BG-021, status-bar icons unreadable (fixed).** The default edge-to-edge style follows the phone's dark mode, so the clock, signal and battery were white on a light header. `MainActivity` now forces dark icons (light style) for the status and navigation bars. Verified after the fix: the clock and icons are clearly readable.
- **BG-022, raw technical text on screen (fixed).** Report Details and Notifications showed ISO timestamps (`2026-11-21T13:21:22.170879+00:00`) and errors appeared as `ExceptionClass: message`. New `UiText` formats timestamps as `Nov 21, 2026, 9:21 PM` in the device zone and maps errors to plain sentences (session expired, server problem, can't reach the server, busy service; our own validation sentences are kept, technical text falls back to a generic line). The feed and queue still store the technical text for diagnostics and for the existing unit-test assertions; it is humanized only where displayed. One existing UI test (`MapRecoveryTest`) asserted the old raw wording on screen and was updated to the new wording, keeping its intent. 9 JVM tests cover the mapping and time formatting.
- **CP-48 review items:** the password rules list now says **"Required: at least 8 characters"** and separates **"Recommended, not required"** hints, so it never claims enforcement that does not exist. `completePasswordReset` replacing the session was verified by reading the code: the ViewModel switches accounts off the auth state's user id (`observeAccount`), so a recovered session goes through the normal account-change path, and queue rows stay owner-bound (S4 on the phone).
- **Lint:** returned to **0 errors / 37 warnings** (was 38) by moving `PhotoCompressor` to `androidx.exifinterface` (the recommended class); the test uses the platform class deliberately and is annotated.

## Phase 3: `PhotoCompressor` real-camera format hardening (BG-023, hardening)

The CP-46 observation (`Cannot decode the selected image.` on one of the owner's real gallery photos) could not be reproduced with synthetic JPEG, PNG, WebP, 12 MP or 108 MP inputs, and the photo itself was deliberately not inspected, so the **root cause remains unconfirmed**. Hardening added: when BitmapFactory cannot read the bounds or returns no bitmap, Android 9+ falls back to `ImageDecoder` (software allocator, `setTargetSize` bounded to 1280 px, orientation applied by the decoder so it is not applied twice, re-encoded as a clean JPEG with no EXIF or GPS). Corrupt, empty and non-image input still raise `Cannot read the selected image.`, a vanished source stays a distinct failure, and BG-012 temp-file cleanup is unchanged. Six deterministic fallback tests (forced through a debug-only hook): orientation applied once and GPS stripped, 8000x6000 and 108 MP bounded, PNG and WebP, corrupt/empty/non-image, truncated JPEG, vanished source. **Failing control:** with the fallback disabled, 4 of the 17 tests fail; restored, 17/17 on the phone. Whether this fixes the owner's specific photo is unknown; if it recurs, note its type.
